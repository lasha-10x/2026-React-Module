# პრეზენტაციის ტექსტი: 10X Shop

ტექსტი განკუთვნილია 5-სლაიდიანი პრეზენტაციისთვის და ცოცხალი დემოსთვის (დაახლოებით 7-8 წუთი). თითოეულ სლაიდს აქვს სათაური, ეკრანზე დასაწერი მოკლე ფრაზა და ის, რასაც ხმამაღლა იტყვი. ციფრები, რომლებიც აქ წერია (87.8 კბ, 191 შემოწმება), რეალურად გაზომილია; Lighthouse-ის ქულები გაზომე შენი deploy-ის შემდეგ და ჩაწერე ხელით.

---

## სლაიდი 1. რა არის 10X Shop

**ეკრანზე:** „10X Shop: ონლაინ მაღაზია React-ზე, TypeScript-ზე და Tailwind-ზე“, ლოგო და ცოცხალი ბმული.

**რას ვამბობ:** მე ავაწყვე ონლაინ მაღაზია, სადაც მომხმარებელს შეუძლია პროდუქტების დათვალიერება, ძებნა და გაფილტვრა, კალათის შევსება, სისტემაში შესვლა, შეკვეთის გაფორმება და შეკვეთის სტატუსის თვალყური. პროდუქტებს ვიღებ DummyJSON-ის საჯარო API-დან, ხოლო შესვლა, გადახდა და შეკვეთები ბრაუზერში არის სიმულირებული, რადგან ეს სასწავლო პროექტია. მთავარი მიზანი იყო არა მხოლოდ ლამაზი გვერდები, არამედ სწორად აწყობილი, ტიპიზირებული და გატესტილი აპლიკაცია.

---

## სლაიდი 2. ტექნოლოგიები და არქიტექტურა

**ეკრანზე:** React 19, TypeScript (strict), Vite, Tailwind v4, React Router, Formik + Yup. ქვემოთ საქაღალდეების სქემა: api, types, models, context, hooks, components, pages, routes, utils.

**რას ვამბობ:** კოდი დაყოფილია ფენებად. `types` შეიცავს მონაცემთა აღწერებს, `api` სერვერთან მუშაობს, `models` შეიცავს ბიზნეს-ლოგიკას ინტერფეისის გარეშე (მაგალითად, კალათის ფასების გამოთვლას), `context` ინახავს გლობალურ მდგომარეობას, `hooks` გამოსაყენებელი ინსტრუმენტებია, ხოლო `pages` და `components` მხოლოდ ხატავენ ეკრანს. მონაცემი მიედინება ერთი მიმართულებით: API ან localStorage, შემდეგ ჰუკი ან კონტექსტი, გვერდი, კომპონენტი. მოქმედება კი უკან მიდის: ღილაკი იძახებს კონტექსტის ფუნქციას, მდგომარეობა იცვლება და ეკრანი თავისით ახლდება. სხვა ბიბლიოთეკა, გარდა ხუთი ნებადართულისა, არ გამომიყენებია.

---

## სლაიდი 3. რა ფუნქციები აქვს

**ეკრანზე:** ძირითადი გზა: კატალოგი, პროდუქტი, კალათა, შესვლა, checkout, შეკვეთა. გვერდით: ძებნა, კატეგორია, სორტირება, გვერდები URL-ში; მიმოხილვები; პრომოკოდი 10X10; პროფილი; dark mode; wishlist.

**რას ვამბობ:** ძირითადი მოთხოვნები სრულად შესრულებულია. დამატებით გავაკეთე FULL დონის ფუნქციები: ძებნა 400 მილიწამიანი debounce-ით, კატეგორია, სორტირება და გვერდები, რომლებიც URL-შია შენახული, ამიტომ ბმულის გაზიარება და Back/Forward მუშაობს. პროდუქტზე არის მიმოხილვები და მსგავსი პროდუქტები, კალათაში პრომოკოდი, ხოლო შეკვეთის სტატუსი (Processing, Shipped, Delivered) დროიდან გამოითვლება და ეკრანზე თავისით იცვლება. ბონუსად დავამატე dark mode, wishlist და ბადის/სიის გადამრთველი. checkout-ზე სავალდებულო ოთხი ველია, ტელეფონი, ინდექსი და ქვეყანა კი არასავალდებულოა, რადგან CORE-ის სპეციფიკაცია ოთხველიან ფორმას აღწერს.

## სლაიდი 4. ხარისხი: ტიპები, ტესტები, პრობლემები

**ეკრანზე:** „0 `any`; 55 unit ტესტი; 114 ბრაუზერული ტესტი; 22 სტატიკური შემოწმება; axe: 0 სერიოზული ხარვეზი“. ქვემოთ სამი ნაპოვნი ბაგი.

**რას ვამბობ:** TypeScript-ი მკაცრ რეჟიმშია და `any` აკრძალულია ESLint-ით, რაც დამატებით ტესტითაც შევამოწმე. ლოკალური მეხსიერებიდან წაკითხული ყველა მონაცემი გადის type guard-ში, ამიტომ დაზიანებული JSON აპლიკაციას ვერ გააფუჭებს. ტესტები ორ დონეზეა: unit ტესტები ამოწმებს ფორმულებს და წესებს, ბრაუზერული ტესტები კი რეალურ ბრაუზერში გადის მთელ გზას და თითოეული ტესტი მოთხოვნის ნომერზეა მიბმული. ტესტირებამ რეალური ხარვეზები აღმოაჩინა და მათი გასწორება DEBUG-LOG-შია აღწერილი. მაგალითად: ველიდან გასვლისას შეცდომის ტექსტი ღილაკს ქვემოთ წევდა და პირველი დაწკაპება იკარგებოდა; ან პროფილიდან გასვლისას მომხმარებელი კატალოგის ნაცვლად login-ზე ხვდებოდა, რადგან ორი რამ ერთმანეთს უსწრებდა.

## სლაიდი 5. შედეგი, შეზღუდვები და შემდეგი ნაბიჯები

**ეკრანზე:** Lighthouse-ის ქულები (შენი გაზომვა), მთავარი JS ფაილი 87.8 კბ gzip; „შემდეგ: რეალური ავტორიზაცია, სერვერული შეკვეთები, Firefox/Safari ტესტი“.

**რას ვამბობ:** მთავარი JavaScript ფაილი 87.8 კილობაიტია gzip-ში, რაც სპეციფიკაციის 250 კილობაიტიან ლიმიტზე ბევრად ნაკლებია, რადგან გვერდები `lazy`-ით იტვირთება და Formik-ი მხოლოდ login გვერდზე ჩამოდის. პროექტს აქვს ცნობილი შეზღუდვები: შესვლა და გადახდა სიმულირებულია, მონაცემები ინახება მხოლოდ ბრაუზერში, ხოლო ტესტები გავუშვი Chromium-ზე სიმულირებული API-ით, ამიტომ Firefox-ზე, Safari-ზე და რეალურ API-ზე ხელით შემოწმება ჯერ ღია საკითხია. შემდეგ ეტაპზე ჩავანაცვლებდი სიმულირებულ ავტორიზაციას რეალური API-ით და ტესტებს თავიდანვე ფუნქციებთან ერთად დავწერდი.

## ცოცხალი დემოს სცენარი (3-4 წუთი)

დაიწყე კატალოგიდან: ჩაწერე ძებნაში „phone“ და აჩვენე, რომ მისამართში ჩნდება `?q=phone`; შეცვალე სორტირება და გადადი მეორე გვერდზე. გახსენი ერთი პროდუქტი, აჩვენე გალერეა, მიმოხილვები და მსგავსი პროდუქტები, დაამატე 2 ცალი კალათაში. კალათაში ჩაწერე პრომოკოდი `10X10` და აჩვენე ჯამების ცვლილება. დააჭირე „Proceed to checkout“: სტუმარს login-ზე გადაგიყვანს, შედი (`emilys` / `emilyspass`) და ავტომატურად დაბრუნდები checkout-ზე. ჯერ დააჭირე „Place order“ ცარიელ ფორმაზე, რომ ვალიდაცია გამოჩნდეს, შემდეგ შეავსე ოთხი ველი და გააფორმე შეკვეთა. გახსენი შეკვეთა, აჩვენე სტატუსი და ერთ წუთში მისი ცვლილება. ბოლოს ჩართე dark mode და გახსენი `/crash-test`, რომ Error Boundary გამოჩნდეს.

## შესაძლო კითხვები და მოკლე პასუხები

**რატომ არ გამოიყენე Redux?** პროექტის ზომაზე Context და `useReducer` საკმარისია, ხოლო კალათის reducer სუფთა ფუნქციაა, რომელიც ისევე ტესტირდება, როგორც Redux-ის reducer.

**რატომ არის URL მდგომარეობის წყარო კატალოგში?** ასე ბმულის გაზიარება, განახლება და Back/Forward ყოველგვარი დამატებითი კოდის გარეშე მუშაობს.

**რა ხდება, თუ ნელი პასუხი ახალს გადაფარავს?** `useFetch` ძველ მოთხოვნას აუქმებს `AbortController`-ით და შედეგს ახსოვს, რომელი მისამართისთვის მოვიდა, ამიტომ ძველი შედეგი ეკრანზე ვერ გამოჩნდება.

**რატომ არ ინახება შეკვეთის სტატუსი?** რადგან ის დროზე დამოკიდებული მნიშვნელობაა; შენახული სტატუსი ძველდებოდა და სინქრონიზაცია დაგვჭირდებოდა, გამოთვლილი კი ყოველთვის სწორია.

**რატომ დაზიანებულ localStorage-ს არ ეშინია აპლიკაციას?** ყველა წაკითხული მნიშვნელობა `unknown` ტიპიდან გადის type guard-ში; თუ ფორმა არ ემთხვევა, ვიყენებთ ცარიელ მნიშვნელობას.

**რა გააკეთა AI-მ და რა შენ?** AI-მ დაწერა კოდის დიდი ნაწილი, ტესტები და დოკუმენტების მონახაზები; მოთხოვნები, გადაწყვეტილებები (მაგ. ბონუსები და CORE-ის პრიორიტეტი), გადამოწმება, deploy და რეალური ციფრები ჩემია. REPORT.md-ში ეს გარკვევით წერია.
